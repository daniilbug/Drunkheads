# Мультиплеер — обязательный стандарт

Применяй при изменении общего состояния мира, RPC, спавна, authority и сетевых сцен. Транспорт — встроенный ENet Godot; host имеет peer ID `1`.

## Владение состоянием

| Состояние | Владелец и существующий механизм |
| --- | --- |
| Движение и ввод обычного Player | Его peer; authority задаётся в `_enter_tree()` из имени узла; `MultiplayerSynchronizer` передаёт позицию и свойства игрока |
| Внешность, поездка и нахождение в душе Player | Сервер; отдельный `AppearanceSynchronizer` остаётся под authority `1` |
| NPC, транспорт, двери, переносимые предметы и общее окружение | Сервер; клиенты отправляют запросы, получают свойства и события |
| Локальные HUD, камера, телефон, настройки и `PlayerData` | Локальный экземпляр игрока; сам `Resource` не обеспечивает сетевую репликацию |
| Мини-игры | Их существующий session/interact узел и схема RPC; подробности в [правилах мини-игр](minigames.md) |

- Сохраняй это распределение. Перед добавлением свойства определи его владельца и обнови нужный synchronizer либо RPC. `@export` само по себе не синхронизирует свойство.
- Для Player сохраняй разделение двух synchronizer; для NPC используй серверную authority. Настраивай authority до работы сети, как в существующих `_enter_tree()`.

## Запросы, свойства и события

- В публичной точке действия сохраняй схему «host вызывает серверный обработчик, client посылает запрос `.rpc_id(1, ...)`». RPC-запрос принимает `any_peer`, проверяет серверную роль и определяет игрока через `multiplayer.get_remote_sender_id()`.
- Если запрос передаёт player ID, проверяй его соответствие отправителю, как в обработке питья и курения. Проверяй применимые предусловия действия в серверном обработчике по существующим образцам: принадлежность предмета, занятость, текущий режим, дистанцию или пересечение зоны.
- Серверные события объявляй с authority сервера; `call_local` используй там, где результат должен примениться также на host. Учитывай локальный вызов, у которого remote sender может быть `0`.
- Надёжные RPC продолжай для дискретных действий и переходов. Для частых обновлений футбола сохраняй `unreliable_ordered`; не меняй транспорт существующего потока в рамках несвязанной правки.
- У нового сетевого поля настрой `SceneReplicationConfig` в `.tscn`: путь, передачу при спавне и подходящий режим обновления по образцу соседних свойств.
- Динамические общие объекты создаёт сервер. Регистрируй соответствующий PackedScene в `MultiplayerSpawner` и сохраняй правильный `spawn_path`; данные и имя для спавна задавай до `add_child()`.
- Сохраняй одинаковые пути RPC-узлов на peers и уникальные стабильные имена сетевых объектов. Игрок именуется строкой peer ID; отрицательные ID выделены NPC.
- Новое состояние должно попадать и к поздно подключившемуся клиенту: через spawn-свойства, synchronizer или snapshot, соответствующий подсистеме. Однократное событие не хранит состояние для будущего подключения.
- Освобождай предметы, места, очереди и ссылки игрока в существующем пути disconnect/leave затронутой системы.

## Локальные данные

Продолжай существующий путь изменения `PlayerData` и подтверждений конкретного действия. Например, автомат списывает деньги локально и возвращает их при отказе, а `PokerSession` отдельно ведёт игровые фишки. Изменение этой модели экономики требует согласования архитектуры; новый код должен явно учитывать, где хранится изменяемая величина.

Образцы: `scripts/menu.gd`, `scripts/main.gd`, `scripts/core/player.gd`, `scripts/levels/bar.gd`, `scripts/core/seat.gd`, `scripts/street/cigarette_machine.gd` и их `.tscn`.
